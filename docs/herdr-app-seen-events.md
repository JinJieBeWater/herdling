# Herdling Core and Herdr App `seen` events

**Scope:** Read-only source investigation of upstream Herdr App `v0.1.10` and current upstream `master` (resolved from `origin/master` to `9af0ecc182dee71d18b73673943f44ac7d2e539b` on 2026-10-31). No live App/Core calls, launches, GUI interaction, or configuration changes were made.

## Finding

There is no public external App event subscription for `seen` in the inspected versions. Core's `events.subscribe` reports Core terminal lifecycle/status, not whether the person viewed a finished agent. The App computes seen from its active window and visible terminal addresses, then persists that attention in its private `view.json`.

The accepted non-polling integration is to watch for `view.json` filesystem invalidations and then query `herdr-app ls` for authoritative current status. This avoids deriving state from the private file and requires no App mod or upstream API. `NSWorkspace` App lifecycle notifications supplement watcher startup, shutdown, and recovery; they are not a source of seen transitions. The watcher is only a wake-up signal: persistence is conditional, can fail, may coalesce state changes, and `view.json` is a private format without compatibility guarantees. The exact persistence constraints and recovery limits are documented below.

## Evidence

1. **App owns the `seen` bit and derives the visible status.** In `model.rs`, `Agent.seen` is App state; Core status updates set it according to whether the App was looking, `mark_seen` clears unseen attention, and `status()` maps an unseen finished word to `done`, otherwise to `idle`: [v0.1.10 model](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/model.rs#L51-L65), [status and seen rules](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/model.rs#L437-L503). The same code is present at the inspected current upstream commit: [current model](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/model.rs#L402-L465).

2. **The App's decision uses active-window visibility, not merely OS app focus.** `visible_addresses()` combines terminals shown in the tab/chrome/agent blocks. `sync()` calls `mark_seen` only when `window_active`, then publishes and saves. So switching panes while the same App window is active can cause the `done` → `idle` transition. [v0.1.10 window](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/window.rs#L1315-L1319) [visible addresses and sync](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/window.rs#L1315-L1454); [current upstream window](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/window.rs#L1259-L1267) [seen then publish](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/window.rs#L1387-L1393).

3. **Core's event API is distinct and suitable for Core status, not App seen.** The App itself subscribes through `events.subscribe`; the result seeds a snapshot (`seq`, `terminals`) and subsequent events update terminal records. Its event parser handles `status`, `finished`, `created`, etc.; there is no App-visible `seen` field/event. [v0.1.10 Core client](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/hc.rs#L31-L158) [subscribe](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/hc.rs#L379-L382); [current upstream Core client](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/hc.rs#L28-L43) [subscribe](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/hc.rs#L354-L365).

4. **A mod can observe the derived transition without polling.** The public mod declaration documents `AgentInfo.status`: “done” means it finished while the person was not looking and becomes “idle” once they look; `agents()` is the live list. [v0.1.10 API declaration](https://github.com/herdrdev/herdr-app/blob/v0.1.10/defaults/herdr.d.ts#L142-L176); [current API declaration](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/defaults/herdr.d.ts#L142-L182). App publishes its computed agents, refreshes mods when published state changes, and the mod host exposes `agents()`: [v0.1.10 publish/refresh](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/window.rs#L1530-L1535) and [host API](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/mods.rs#L950-L970); [current upstream refresh](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/window.rs#L1446-L1454) [publish agents](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/window.rs#L1526-L1535).

5. **The App control socket is synchronous request/reply, not a subscriber.** It serves one JSON-line request and writes one JSON-line response. The exposed CLI verbs include `status`/`ls` and `do`; there is no watch/subscribe verb in this interface. [v0.1.10 control socket](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/control.rs#L1-L57) [client verbs](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/control.rs#L68-L100); [current upstream](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/control.rs#L1-L57) [verbs](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/control.rs#L68-L100).

6. **Native notifications do not provide an inbound `seen` signal here.** The inspected sources implement App notifications as App toast overlays and play attention sounds; the agent status documentation attributes the semantic `done` → `idle` change to looking at the agent. No macOS notification observer/Accessibility observer or incoming notification hook was found in the `v0.1.10` source. An OS-level observer would not be the documented contract for App's derived state. [v0.1.10 mod notification API](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/mods.rs#L995-L1007); [alert handling](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/window.rs#L1910-L1947); [status semantics](https://github.com/herdrdev/herdr-app/blob/v0.1.10/defaults/herdr.d.ts#L142-L160).

## Practical route and limits

- Watch the App home directory for `view.json` replacement. On a relevant invalidation, coalesce notifications, call `herdr-app ls`, and compare its returned statuses to the last authoritative snapshot. Do not parse `view.json` to determine seen state. Use the running App's home (`HERDR_APP_HOME` override, otherwise the documented defaults) and account for atomic replacement and symlink targets.
- Use `NSWorkspace` App lifecycle notifications only to supplement watcher lifecycle and recovery, such as arming/re-arming when the App launches and refreshing after it reopens. They do not indicate seen state; `view.json` invalidation followed by `ls` remains the seen-state route.
- `herdr-app ls` returns the current world/status snapshot; `herdr-app status` returns window metadata and errors. Neither exposes a subscription. Core events can signal Core status changes but do not certify App seen. The App's persisted view only updates when a Core document is loaded, serialized view differs, and the atomic write succeeds. Notifications can coalesce, and a state that changes and returns before `ls` may be observed only in its final state.
- `view.json` is private App persistence with no compatibility guarantee. Keep a startup/reconnect/overflow recovery read of `ls`; compare snapshots so navigation writes or startup activity do not become false status transitions. `seen.json` stores discovered mod IDs and is unrelated to agent attention.

## Follow-up: persisted view as an event-driven invalidation source

**Conclusion: yes.** A filesystem watcher can replace polling as the wake-up trigger. Watch the App home directory for the atomic replacement of **`view.json`**, then call `herdr-app ls` and compare its returned statuses with the last authoritative snapshot. Do not read `seen.json` to infer agent state, or treat `view.json` contents as the returned status. This is a source-supported persistence behavior, though it is not a documented external event API.

### Why this works

- `view.json` is documented as storing this screen's “seen attention”; `seen.json` is grouped with mod state/bookkeeping. The App reads `seen.json` into a set of mod IDs, and inserts a mod ID there when it records a newly discovered mod. [v0.1.10 file table](https://github.com/herdrdev/herdr-app/blob/v0.1.10/defaults/AGENTS.md#L63-L75) [read mod seen set](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/window.rs#L420-L425) [write discovered mod ID](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/window.rs#L3457-L3472).
- The persisted `View` captures an `attention` map from each agent address to its Core word plus App-owned `seen` boolean. On restore, the App reapplies the saved `seen` only when the current word still matches the saved word. [v0.1.10 capture/restore](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/mirror.rs#L35-L55) [capture and apply](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/mirror.rs#L134-L205); [current capture](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/mirror.rs#L134-L143).
- On an active window sync, the App marks visible addresses seen, then publishes and calls `save()`. `save()` calls `save_view()`, which serializes the captured model and writes `view.json` when at least one Core document is loaded and the serialized view differs from its last written version. Thus a real unseen → seen transition changes this persisted representation; ordinary focus/selection/view changes can also change the file. [v0.1.10 sync](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/window.rs#L1384-L1393) [save and save_view](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/window.rs#L977-L1017); [current sync](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/window.rs#L1387-L1393) [current save_view](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/window.rs#L1010-L1020).
- The write goes to a sibling temporary file and renames it over the destination; App code explicitly documents this as avoiding partial reads. The App home comes from `HERDR_APP_HOME`, else XDG config, else `~/.config/herdr-app`. [atomic writer](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/persist.rs#L21-L37) [path resolution](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/mods.rs#L41-L46). Monitor the parent directory (or the resolved target's parent if `view.json` is a symlink), because the file node is replaced.
- `herdr-app ls` is the authoritative follow-up read: the control handler returns `self.world()`, whose terminal records use `m.status(addr)`. `status` only returns window metadata/errors. Both handlers are read paths; neither calls `save()` or writes `view.json`, so querying `ls` does not itself create a write loop. [v0.1.10 control dispatch and world](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/window.rs#L3286-L3357). The `ls`/`status` clients are one-request/one-response over the local control socket: [control client](https://github.com/herdrdev/herdr-app/blob/v0.1.10/src/control.rs#L68-L110).
- Current upstream `master` at the pinned commit retains the same `view.json` capture, conditional write, atomic replacement, and `ls` world behavior: [current save_view](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/window.rs#L1012-L1020), [current attention capture](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/mirror.rs#L134-L143), [current atomic writer](https://github.com/herdrdev/herdr-app/blob/9af0ecc182dee71d18b73673943f44ac7d2e539b/src/persist.rs#L21-L37).

### Limits to account for

- This is an invalidation channel, not a one-record-per-transition event log. Multiple changes may coalesce; `view.json` can change for navigation/zoom/recent history as well as attention. On each relevant directory notification, debounce/coalesce, read `herdr-app ls`, and compare the returned App statuses. Keep a startup baseline so startup rewrites do not look like new transitions.
- Persistence is conditional: the view is written only if a Core document is loaded, serialized data differs, and atomic write succeeds. Failures are logged and leave no successful file-replacement event. For visible agents backed by the loaded local Core document, the ordinary active-window seen path reaches `save_view()` in the same sync. Still retain a recovery/read-on-connect path and treat watcher overflow/restart as needing a fresh `ls` snapshot.
- The file is per App home/screen. Resolve the same home as the running App (`HERDR_APP_HOME` overrides the defaults); each distinct home has its own view and control socket. Atomic rename means a direct watcher attached only to the old file vnode can become stale; watch its parent directory and re-resolve/re-arm after replacement. App-owned symlink handling may direct the replacement to the symlink target, so resolve or cover that target directory too.
- The App's public `ls` is a full current state snapshot, not transition history. If a state changes and returns before the consumer reads it, the consumer may see only the final state. This is suitable for state convergence/invalidation, not guaranteed delivery of every transition. `view.json` is private implementation state; upstream may alter it without compatibility guarantees.
